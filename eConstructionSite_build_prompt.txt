Use the existing product/variant selection modal/card as the visual reference.

============================================================
OBJECTIVE
============================================================

The POS must allow the cashier/operator to create an order for a product that is NOT currently available in the product catalogue.

This is called:

SPECIAL ORDER

A Special Order is a manually entered product/order item.

The cashier must be able to enter:

1. Product Name
2. Product Details / Description
3. Quantity
4. Unit Price

The Special Order must then be added to the POS cart.

It must NOT require an existing product ID, SKU, variant, stock record, or catalogue entry.

============================================================
IMPORTANT BUSINESS RULE
============================================================

A Special Order is NOT an existing catalogue product.

Therefore:

- Do not require product_id.
- Do not require variant_id.
- Do not check normal inventory stock.
- Do not deduct stock from an existing product.
- Do not require Size/Color/Variant selection.
- Do not force the cashier to create a catalogue product.
- Do not modify the normal product catalogue.

Instead, create a temporary/manual POS item identified as:

item_type = "SPECIAL_ORDER"

The item should remain clearly identifiable as a Special Order throughout the cart and checkout process.

============================================================
HOW THE USER OPENS SPECIAL ORDER
============================================================

Add a clearly visible button to the POS.

Recommended:

[ + Special Order ]

Possible location:

Near the product search box / Products Available section.

Example:

---------------------------------------------------------

[ + Special Order ]

Products Available: XX
---------------------------------------------------------

Clicking:

[ + Special Order ]

opens the Special Order modal.

# Discount Approval Amendment — Role-Based Approval Hierarchy

**Target:** `https://econstruction-supply.site/supplier/discount-approvals.php`

## Task

Amend the existing **Discount Approval** workflow to implement the following **role-based approval hierarchy**.

The required approval level depends on the role of the user who created the discount request.

### 1. Admin / Manager Creates the Request

If the discount request is created by an:

* **Admin**, or
* **Manager**

the same **Admin / Manager** is authorized to approve the request, subject to the existing discount limits and approval rules.

```text
Admin / Manager
      ↓
Creates Discount Request
      ↓
Admin / Manager Approval
      ↓
APPROVED
```

The system must still enforce all existing discount-limit rules, including the configured maximum and any special/absolute maximum limits.

---

### 2. Cashier / Operator Creates the Request

If the discount request is created by a:

* **Cashier**, or
* **Operator**

the request must **not be self-approved**.

The request requires approval from an authorized:

* **Admin / Manager**, or
* **Supervisor**

```text
Cashier / Operator
        ↓
Creates Discount Request
        ↓
 ┌──────────────────────┐
 │ Admin / Manager      │
 │ OR                   │
 │ Supervisor            │
 └──────────┬───────────┘
            ↓
         APPROVED
```

The Cashier or Operator must not be able to approve, modify, or finalize their own discount request.

---

### 3. Supervisor Creates the Request

If the discount request is created by a **Supervisor**, the Supervisor must not be allowed to approve their own request.

The request requires approval from an authorized:

**Admin / Manager**

```text
Supervisor
     ↓
Creates Discount Request
     ↓
Admin / Manager Approval
     ↓
APPROVED
```

A Supervisor must not approve their own discount request.

---

# 4. Approval Rules Summary

Implement the following matrix:

| Request Created By | Who Can Approve               | Self-Approval                        |
| ------------------ | ----------------------------- | ------------------------------------ |
| Admin              | Admin / Manager               | Allowed according to existing policy |
| Manager            | Admin / Manager               | Allowed according to existing policy |
| Supervisor         | Admin / Manager               | **Not allowed**                      |
| Cashier            | Admin / Manager OR Supervisor | **Not allowed**                      |
| Operator           | Admin / Manager OR Supervisor | **Not allowed**                      |

### Important

For **Cashier/Operator** requests, either an authorized **Supervisor** or **Admin/Manager** may approve the request.

For **Supervisor** requests, only **Admin/Manager** approval is allowed.

---

# 5. Approval Permission Must Be Server-Side

Do not rely only on the frontend to determine who can approve.

The backend must verify:

```text
Requester's Role
+
Approver's Role
+
Supplier/Tenant
+
Approval Permission
+
Discount Limit
+
Request Status
```

before allowing an approval action.

A user must not be able to bypass the approval hierarchy by modifying:

* User ID
* Role
* Request ID
* Supplier ID
* Tenant ID
* Approval level
* Approval status
* Discount percentage

through browser developer tools or manipulated API requests.

# 33. CHANGE ONLY WHAT IS REQUIRED

The AI agent must follow a **minimal-change strategy**.

Before modifying a component:

1. Identify its current purpose.
2. Identify which pages use it.
3. Identify dependencies.
4. Determine whether it can be safely reused.
5. Make the smallest required change.
6. Test all affected pages.

Do not rewrite working modules simply because a different implementation appears cleaner.

# 36. FINAL STANDARDIZATION MODEL

The eConstruction Supply platform should use the following standardized model:

```text
                         eCONSTRUCTION SUPPLY
                                  │
                ┌─────────────────┴─────────────────┐
                │                                   │
          MARKETPLACE                            SUPPLIER
           index.php                             store.php
                │                                   │
        ALL SUPPLIERS                         ONE SUPPLIER
                │                                   │
      Optional Supplier Filter              Locked Supplier Scope
                │                                   │
                └─────────────────┬─────────────────┘
                                  ↓
                         STANDARD PRODUCT CARD
                                  ↓
                           + ADD / SELECT
                                  ↓
                        STANDARD VARIANT MODAL
                                  ↓
                            SELECT QUANTITY
                                  ↓
                            EXISTING CART
```

### Page responsibilities

```text
index.php
= Marketplace-wide product discovery

store.php?slug={supplier}
= Supplier-specific product discovery

product-category.php
= Category-specific product discovery

supplier/pos.php
= Supplier/Tenant-specific POS operations
```

### Most important rule

**Standardize the presentation, not the data scope.**

The same Product Card, Variant Modal, Active Filters, Search, Sort and responsive design should provide a consistent user experience across the platform.

But:

```text
Homepage
→ Marketplace-wide

Supplier Store
→ One supplier only

Category Page
→ Existing category scope

POS
→ Logged-in supplier/tenant scope
```

Never allow UI standardization to weaken supplier/tenant isolation or alter existing business functionality.

**Implement the smallest safe change necessary to achieve this standardization.**

# UNIFIED "SEND PURCHASE ORDER" WORKFLOW

## Objective

Implement a **single, consistent Purchase Order submission workflow** for both the Customer checkout page and the Supplier POS checkout page.

There are two different checkout entry points used by two different user types:

| User                   | Checkout Page            | Role                              |
| ---------------------- | ------------------------ | --------------------------------- |
| Customer               | `/checkout.php`          | Customer                          |
| Order Processing Staff | `/supplier/checkout.php` | Order Processing Staff / Operator |

Although the two pages are located in different directories and are used by different users, **the "Send Purchase Order" action must use the same underlying order-submission/business process**.

After a successful **Send Purchase Order**, both pages must redirect to:

```text
https://econstruction-supply.site/supplier/paid-orders.php
```

---

# 1. CUSTOMER CHECKOUT

## Target

```text
https://econstruction-supply.site/checkout.php
```

This page is used by the **Customer**.

Locate the existing:

```html
<div class="col-md-12 form-group" style="margin-top: 10px;">
    <input type="submit"
           class="btn btn-primary"
           style="background-color: #0284c7;
                  border-color: #0284c7;
                  font-size: 16px;
                  padding: 10px 20px;"
           value="Send Purchase Order"
           name="form_otc">
</div>
```

Keep the button label:

```text
Send Purchase Order
```

When the Customer clicks **Send Purchase Order**, the system must:

1. Validate the checkout information.
2. Validate the current cart/order.
3. Create/submit the Purchase Order using the existing order-processing logic.
4. Save the order correctly in the existing database structure.
5. Preserve the Customer, Supplier/Tenant, products, quantities, prices, discounts, totals, and order information.
6. Prevent duplicate order creation.
7. After successful submission, redirect to:

```text
/supplier/paid-orders.php
```

# 3. IMPORTANT — SAME SUBMISSION PROCESS

The two pages:

```text
https://econstruction-supply.site/checkout.php
```

and:

```text
https://econstruction-supply.site/supplier/checkout.php
```

must be treated as **two different entry points into the same Purchase Order workflow**.

The implementation should NOT create two separate business processes.

Conceptually:

```text
                    PURCHASE ORDER SUBMISSION
                              │
             ┌────────────────┴────────────────┐
             │                                 │
             ▼                                 ▼
      CUSTOMER CHECKOUT                  SUPPLIER POS CHECKOUT
      /checkout.php                      /supplier/checkout.php
             │                                 │
             │      Send Purchase Order        │
             └───────────────┬─────────────────┘
                             ▼
                  SAME ORDER SUBMISSION LOGIC
                             │
                             ▼
                    CREATE/SAVE ORDER
                             │
                             ▼
              SUCCESSFUL SUBMISSION
                             │
                             ▼
          /supplier/paid-orders.php
```

Do not duplicate the same order-creation code unnecessarily.

---

# 5. IMPORTANT DISTINCTION: ORDER STATUS VS PAYMENT STATUS

Do not assume that an order is already paid merely because the customer clicked:

```text
Send Purchase Order
```

The **Send Purchase Order** action means:

```text
Purchase Order submitted
```

It does NOT automatically mean:

```text
Payment completed
```

Therefore, preserve the application's existing order/payment status model.

If the existing system has a specific status representing:

```text
Pending Payment
Awaiting Payment
Unpaid
PO Submitted
```

use that existing status.

Do not mark the order as `PAID` unless payment has actually been confirmed.

# 8. SUPPLIER/TENANT ISOLATION

This is a multi-tenant application.

The implementation must preserve the existing Supplier/Tenant relationship.

For orders submitted from:

```text
/supplier/checkout.php
```

the system must use the authenticated Order Processing Staff/Operator's existing Supplier/Tenant context.

For orders submitted from:

```text
/checkout.php
```

the system must preserve the existing Customer → Supplier relationship.

Never allow an order submitted by one Supplier/Tenant to appear as another Supplier/Tenant's order.

Do not remove or weaken existing authorization checks.

---

* Order/PO number

* Products
* Product variants

* Unit prices
* Discounts
* Discount approval information, if applicable

* Payment status
* Created-by user, where supported
* Existing audit information

# 10. PREVENT DUPLICATE ORDERS

The system must protect against duplicate Purchase Orders caused by:

* Double-clicking **Send Purchase Order**
* Browser refresh
* Form resubmission
* Network retry
* Back/forward browser navigation

Use the application's existing duplicate-submission/idempotency mechanism if one exists.

Do not create duplicate orders or duplicate payment records.

---

# 11. ERROR HANDLING

If order creation fails:

* Do NOT redirect to `/supplier/paid-orders.php`.
* Do NOT create a partial order.
* Display the existing error handling/message mechanism.
* Preserve the user's entered information where possible.

Redirect to:

```text
/supplier/paid-orders.php
```

ONLY after successful Purchase Order creation/submission.
